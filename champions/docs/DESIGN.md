## 1. 作るものと前提

| 機能 | 内容 |
|---|---|
| 1. 個体の作成と能力値の計算 | ポケモン・性格・能力ポイントなどを入力すると、実数値をその場で表示 |
| 2. チームの編成 | 保存した個体から最大6体を選んでチームを作る(最大10チーム) |
| 3. ダメージ計算 | 攻撃側・防御側・技・条件を選ぶと、ダメージと確定数を表示 |

**ゲームの仕様(必ず守るもの)**

- レベル50固定、個体値なし(すべて最大扱い)
- 能力ポイントは合計66まで、1つの能力に32まで
- `HP = 種族値 + 75 + 能力ポイント`
- `HP以外 = floor((種族値 + 20 + 能力ポイント) × 性格補正)` (性格補正は 1.1 / 1.0 / 0.9)
- バトルギミックは現在メガシンカのみ。将来の追加(テラスタル、ダイマックスなど)に備える

**置き場所**

このリポジトリの `champions/` フォルダの中に作ります。
すでにある AI-901 クイズ(`index.html`)には手を触れません。

## 2. 技術の選定

**React + Vite + TypeScript** で作ります(3案から選択済み)。

| 道具 | 役割 | ひとことで言うと |
|---|---|---|
| TypeScript | 言語 | JavaScript に「型」(データの形の宣言)を足したもの。書き間違いを実行前に教えてくれる |
| React | 画面 | 「データが変わったら画面が自動で描き直される」仕組みを提供するライブラリ |
| Vite | 開発サーバー・ビルド | 開発中はファイルを保存するたびに画面を即更新。公開用のファイルもまとめて作る |
| Vitest | テスト | 計算結果が期待どおりかを自動で確かめる道具(Vite と設定を共有できる) |
| idb | 保存 | ブラウザの IndexedDB を書きやすくする小さなライブラリ |
| vite-plugin-pwa | PWA | ホーム画面に追加できるようにするための部品を自動で作る |

**この案を選んだ理由**

- 入力するたびに実数値・残りポイント・ダメージを再表示する画面が多く、React の考え方と合う
- 個体データやギミックの「形」を TypeScript の `interface` としてコードに書ける。
  今回の「拡張しやすい設計」という要件にいちばん合う
- テストと PWA 化を Vite がまとめて面倒を見てくれる

**あえて使わないもの**(覚えることを増やさないため)

- 状態管理ライブラリ(Redux など) → React 標準の機能で足りる
- CSS フレームワーク(Tailwind など) → 素の CSS で書く。スマホ対応の基本が身につく
- ルーター(画面の URL 管理) → 最初は「いまどの画面か」を変数で持つだけにする。必要になったら足す

**比較した他の案**

| 案 | 良い点 | 見送った理由 |
|---|---|---|
| React + Vite + JavaScript | 型を覚えなくてよい | データの形の間違いに実行するまで気づけない |
| 素の HTML/CSS/JavaScript | 道具が不要、ブラウザの基礎が学べる | 入力項目が多い画面で、画面の書き換え処理が絡まりやすい |

## 3. 画面一覧

スマホ(縦画面)では画面下にタブ、PC では上部にナビゲーションを置きます。

```
スマホ                          PC
+------------------------+      +------------------------------------------+
|  個体一覧       12/500 |      | [個体] [チーム] [ダメージ計算] [設定]    |
|                        |      +------------------------------------------+
|  (画面の中身)          |      |                                          |
|                        |      |   (画面の中身。横に広く使う)             |
+------------------------+      |                                          |
| 個体 | チーム|ダメ計|設定|      +------------------------------------------+
+------------------------+
```

| # | 画面 | できること |
|---|---|---|
| 1 | 個体一覧 | 保存した個体の一覧・検索、新規作成、複製、削除。件数表示(例: 12/500) |
| 2 | 個体編集 | ポケモン、ニックネーム、性格、特性、持ち物、技4つ、能力ポイント、ギミック設定。実数値と残りポイントを常に表示 |
| 3 | チーム一覧 | チームの作成、名前変更、並べ替え、複製、削除。件数表示(例: 3/10) |
| 4 | チーム編集 | 保存した個体から最大6体を選ぶ、メンバーの並べ替え・外す |
| 5 | ダメージ計算 | 攻撃側・防御側(保存個体を呼び出す/その場で作る)、技、条件、結果 |
| 6 | 設定 | レギュレーションの切り替え、JSON の書き出し/読み込み、データの出典表示 |

ダメージ計算画面のレイアウト:

- スマホ: 攻撃側 → 技 → 防御側 → 条件 を縦に並べ、**結果は画面下に固定**して常に見えるようにする
- PC: 「攻撃側 | 条件と結果 | 防御側」の3列

## 4. 全体の構造(層に分ける)

プログラムを役割ごとの「層」に分けます。大事なのは**矢印の向き**です。

```
画面        src/features/  src/components/
  |           React。入力を受け取って結果を表示するだけ。計算式は書かない
  |
  +--呼ぶ-->  計算      src/calc/  src/gimmicks/
  |             ただの関数の集まり。画面のことも保存のことも知らない
  |             → 画面なしで単体テストできる
  |
  +--呼ぶ-->  保存      src/storage/
  |             IndexedDB への読み書き、JSON 書き出し/読み込み、マイグレーション
  |
  +--読む-->  マスターデータ   src/data/*.json
                種族値・技・特性・持ち物など。読み取り専用
```

- 「計算」は「画面」や「保存」を**呼ばない**。これを守ると、計算だけを取り出してテストできます
- 用語: 同じ入力なら必ず同じ結果を返し、外の世界(画面や保存)を変えない関数を**純粋関数**と呼びます。
  計算の層はすべて純粋関数で書きます

## 5. データ構造

データは3種類あります。

| 種類 | 例 | 置き場所 | 変わるか |
|---|---|---|---|
| マスターデータ | 種族値、技の威力 | `src/data/*.json` | アプリ利用中は変わらない |
| 保存データ | 自分が作った個体・チーム | ブラウザの IndexedDB | 利用者が変える |
| 一時データ | 計算画面で試しに変えた値 | メモリの中だけ | 画面を閉じると消える |

### 5.1 マスターデータ(JSON)

**方針: 保存データは「ID」で参照する。** 表示名(日本語)を保存データに書かないので、
あとで表示名を直しても保存済みの個体は壊れません。ID は英小文字とハイフン(例: `garchomp`)にします。

`pokemon.json` の1件(形式の例。メガシンカ後の数値はステップ1で出典から取得して入れます):

```json
{
  "id": "garchomp",
  "name": "ガブリアス",
  "types": ["dragon", "ground"],
  "baseStats": { "hp": 108, "atk": 130, "def": 95, "spa": 80, "spd": 85, "spe": 102 },
  "abilities": ["sand-veil", "rough-skin"],
  "megaForms": [
    {
      "id": "garchomp-mega",
      "name": "メガガブリアス",
      "requiredItem": "garchompite",
      "types": ["…"],
      "baseStats": { "…": "…" },
      "ability": "…"
    }
  ]
}
```

| ファイル | 中身 | 1件の形 |
|---|---|---|
| `pokemon.json` | ポケモン | 上の例 |
| `moves.json` | 技 | `{ id, name, type, category, power, target }` |
| `abilities.json` | 特性 | `{ id, name }` |
| `items.json` | 持ち物 | `{ id, name }` |
| `natures.json` | 性格 | `{ id, name, up, down }` (補正なしは `up`/`down` が `null`) |
| `types.json` | タイプ名と相性表 | 18タイプ × 18タイプ |
| `regulations.json` | レギュレーション | `{ id, name, gimmicks }` (6.5 で説明) |
| `sources.json` | 出典の記録 | どのデータを、どこから、いつ取得したか |

能力の名前は全体で次の6つに統一します: `hp` `atk` `def` `spa` `spd` `spe`

**特性・持ち物の「効果」はどこに書くか**

- 名前などの表示用データ → JSON
- ダメージへの補正(計算の決まり) → コード(`src/calc/damage/rules/`)に、ID を見出しにして書く
- JSON にあってもコードに補正が無い特性・持ち物は「ダメージ補正なし」として扱い、
  画面に「補正は未対応」と表示します(黙って無視しない)

### 5.2 保存データ(IndexedDB)

**IndexedDB** はブラウザに組み込まれたデータベースです。データは利用者の端末の中だけに保存されます。

| 保存場所(ストア) | 中身 | 上限 |
|---|---|---|
| `individuals` | 個体 | 500 |
| `teams` | チーム | 10 |
| `meta` | 保存形式のバージョン番号、選択中のレギュレーションなど | - |

**個体(Individual)**

```ts
interface Individual {
  id: string;                    // 自動で作る重複しない文字列
  speciesId: string;             // "garchomp"
  nickname: string;
  natureId: string;              // "jolly"
  abilityId: string;
  itemId: string | null;         // 持ち物なしは null
  moveIds: (string | null)[];    // 技4つ。空欄は null
  statPoints: StatPoints;        // { hp, atk, def, spa, spd, spe } 各0〜32、合計66まで
  gimmicks: GimmickSettings;     // ★使うギミックとその設定
  createdAt: string;             // 作成日時
  updatedAt: string;             // 更新日時
}

interface GimmickSettings {
  mega?: { formId: string };     // あれば「メガシンカする」。無ければ「しない」
  // 将来ここに足す → tera?: { teraType: string };
}
```

保存された個体の例(形式の例):

```json
{
  "id": "0b9c2f6e-…",
  "speciesId": "garchomp",
  "nickname": "ガブ",
  "natureId": "jolly",
  "abilityId": "rough-skin",
  "itemId": "garchompite",
  "moveIds": ["earthquake", "dragon-claw", "rock-slide", "protect"],
  "statPoints": { "hp": 2, "atk": 32, "def": 0, "spa": 0, "spd": 0, "spe": 32 },
  "gimmicks": { "mega": { "formId": "garchomp-mega" } }
}
```

`gimmicks` を「ギミック名 → 設定」の入れ物にしたのがポイントです。

- `mega?` の `?` は「無くてもよい」という意味。メガシンカしない個体は `gimmicks: {}` になる
- 将来 `tera` を足しても、古いデータには `tera` が無いだけ=「未設定」として読める。**古いデータは壊れない**
- 1体が複数のギミックの設定を持てる(例: メガストーンを持ちつつテラスタイプも決めておく)。
  「実際にどれを発動したか」は保存せず、計算画面の一時データとして持つ(5.3)

**チーム(Team)**

```ts
interface Team {
  id: string;
  name: string;
  memberIds: string[];   // 個体の id を最大6つ。この配列の順番=並び順
  order: number;         // チーム一覧での並び順
  createdAt: string;
  updatedAt: string;
}
```

- チームは個体の**コピーではなく id** を持つ。個体を編集すれば、入っているチームにも反映される
- 同じ個体を複数のチームに入れられる。1つのチームに同じ個体を2回は入れられない
- 個体を削除するときは「この個体は◯◯チームに入っています」と知らせ、チームからも外す
- チームの複製は、メンバーの id の並びをコピーする(個体そのものは増やさない)

### 5.3 一時データ(ダメージ計算画面)

```ts
interface BattlerInput {
  individual: Individual;             // 保存個体の「コピー」、またはその場で作ったもの
  sourceId: string | null;            // どの保存個体から呼び出したか(表示用)
  activeGimmick: GimmickId | null;    // いま発動しているギミック
  ranks: { atk; def; spa; spd; spe }; // ランク補正 -6〜+6
  isBurned: boolean;                  // やけど
}
```

保存個体を呼び出すときに**丸ごとコピー**を作り、計算画面ではコピーだけを変更します。
保存の関数を呼ばないかぎり IndexedDB は変わらないので、「一時的な変更」が自然に実現できます。

### 5.4 書き出しファイル(JSON)

```json
{
  "app": "champions-tool",
  "schemaVersion": 1,
  "exportedAt": "2026-11-16T12:00:00.000Z",
  "individuals": [],
  "teams": []
}
```

`schemaVersion` が保存形式のバージョン番号です(6.6 で説明)。

## 6. 拡張の仕組み(バトルギミックの追加に備える)

### 6.1 考え方

ギミックが増えるたびに計算のコードへ `if (メガシンカなら) … else if (テラスタルなら) …` を
書き足していくと、すぐに読めなくなり、直すたびに他の場所を壊します。そこで次のように分けます。

- **変わらない部分**: 能力値の式、ダメージ計算の流れ、保存の仕組み、画面の枠組み
- **差し替える部分**: 個々のギミック(メガシンカ、テラスタル…)

差し替える部分が守る「共通の形」を決めておき、変わらない部分はその形だけを相手にします。
この「共通の形」を**インターフェース**と呼びます。コンセントの形が決まっているから、
どの家電でも挿せるのと同じ考え方です。

### 6.2 ギミックの共通の形

ギミックが起こす変化を4種類に整理し、それぞれを「フック」(決まった場面で呼ばれる関数)にします。

| 変化の種類 | フック | 使うギミックの例 |
|---|---|---|
| 種族値・タイプ・特性を変える | `changeForm` | メガシンカ、テラスタル(タイプ) |
| 実数値を変える(HP など) | `changeStats` | ダイマックス(HP 2倍) |
| 技の威力やタイプを変える | `changeMove` | ダイマックス技、テラバースト |
| ダメージ補正を加える | `getModifiers` | テラスタルのタイプ一致 |

```ts
// src/gimmicks/types.ts (設計時点のスケッチ。細部は実装時に調整します)

/** ギミックが変化させる対象 */
interface BattleForm {
  baseStats: BaseStats;   // 種族値
  types: string[];        // 攻撃を「受ける」ときのタイプ
  stabTypes: string[];    // タイプ一致の判定に使うタイプ
  abilityId: string;      // 特性
}

/** すべてのギミックが守る共通の形 */
interface Gimmick<Config> {
  id: GimmickId;          // 'mega' など。保存データやレギュレーション設定でこの名前を使う
  label: string;          // 画面に出す名前
  canUse(individual, data): boolean;   // この個体で使えるか

  // ここから下が「変化」。必要なものだけ書く(? は「無くてもよい」の印)
  changeForm?(form: BattleForm, config: Config, ctx): BattleForm;
  changeStats?(stats: Stats, config: Config, ctx): Stats;
  changeMove?(move: MoveData, config: Config, ctx): MoveData;
  getModifiers?(config: Config, ctx): Modifier[];
}
```

メガシンカはこの形の**実装の1つ**です。`changeForm` だけを書けば済みます。

```ts
// src/gimmicks/mega.ts (スケッチ)
export const mega: Gimmick<{ formId: string }> = {
  id: 'mega',
  label: 'メガシンカ',
  canUse: (individual, data) => data.species(individual.speciesId).megaForms.length > 0,

  changeForm: (form, config, ctx) => {
    const megaForm = ctx.species.megaForms.find((f) => f.id === config.formId);
    if (!megaForm) return form;          // データが無ければ何も変えない
    return {
      baseStats: megaForm.baseStats,     // 種族値を差し替え
      types: megaForm.types,             // タイプを差し替え
      stabTypes: megaForm.types,
      abilityId: megaForm.ability,       // 特性を差し替え
    };
  },
};
```

使えるギミックは「登録簿」に並べます。変わらない部分は登録簿を通してギミックを呼ぶので、
個々のギミックの名前を知りません。

```ts
// src/gimmicks/registry.ts (スケッチ)
export const gimmickRegistry = { mega };   // 追加するときはここに並べる
```

### 6.3 個体から「戦闘中の姿」を作る流れ

```
保存された個体 (Individual)        … IndexedDB にある設計図
  |
  | (1) 種族データを引く (pokemon.json)
  v
元の姿 (BattleForm)                … 種族値・タイプ・特性
  |
  | (2) gimmick.changeForm()       ← メガシンカ: 種族値・タイプ・特性を差し替え
  v
変化後の姿
  |
  | (3) calcStats(種族値, 能力ポイント, 性格)   … 機能1の式。ギミックのことは知らない
  v
実数値 (Stats)
  |
  | (4) gimmick.changeStats()      ← (将来) ダイマックス: HP 2倍
  v
戦闘中の姿 (Battler)               … ダメージ計算に渡すもの
```

発動中のギミックが無いとき、またはそのフックが書かれていないとき、(2)(4) は素通りします。
個体編集画面の「メガシンカ後の実数値」表示も、この同じ流れを使います。

### 6.4 ダメージ計算は「補正を順番に適用する流れ」

ゲームの補正は、1.5倍を `6144`、1.0倍を `4096` のように**4096を基準にした整数**で持っています
(小数の誤差を避けるため)。このアプリでも同じ整数で持ち、切り捨ての位置まで再現します。

```ts
// src/calc/damage/modifier.ts (スケッチ)
interface Modifier {
  stage: StageId;   // どの段階で効くか ('power' | 'attack' | 'defense' | 'stab' | 'final' など)
  value: number;    // 4096 を 1.0 倍とした整数。1.5倍なら 6144
  label: string;    // 画面に出す説明。例: "こだわりハチマキ"
}
```

特性・持ち物・天気・フィールド・壁・ギミックは、どれも**同じ形の Modifier を返すだけ**にします。

```
攻撃側 Battler + 技 + 防御側 Battler + 場の状態
  |
  | A. 技を確定        gimmick.changeMove()   (将来: ダイマックス技、テラバースト)
  |
  | B. 補正を集める    特性のルール / 持ち物のルール / 天気・フィールド・壁のルール
  |                    / gimmick.getModifiers()        → Modifier の一覧ができる
  |
  | C. 段階の順番表に沿って、上から1つずつ適用
  v
  1 威力 → 2 攻撃 → 3 防御 → 4 基礎ダメージ → 5 範囲 → 6 天気 → 7 急所
  → 8 乱数(16通り) → 9 タイプ一致 → 10 タイプ相性 → 11 やけど → 12 最終補正
  |
  v
ダメージ16通り → 最小〜最大 / HPに対する% / 確定数
```

- 段階の順番と丸め方は**1か所の表**(`stages.ts`)にまとめる。順番を確認したいときはそこだけ見ればよい
- 新しい補正を足すとき、流れの本体(`pipeline.ts`)は触らない。Modifier を返すルールを足すだけ
- 各 Modifier に `label` があるので、結果画面に「適用された補正の内訳」を出せる。計算の検算にも使える

### 6.5 レギュレーションごとに使えるギミックを切り替える

```json
[
  { "id": "sample-mega", "name": "(サンプル) メガシンカあり", "gimmicks": ["mega"] }
]
```

- 設定画面でレギュレーションを選ぶ(選択は `meta` に保存)
- 個体編集画面とダメージ計算画面は、**選択中のレギュレーションの `gimmicks` に入っているものだけ**表示する
- 使えないギミックの設定が個体に残っていても、消さずに無視する(レギュレーションを戻せば復活する)
- 実際のレギュレーション名と内容は、ゲーム内の表示を見て JSON に書き足す

### 6.6 保存形式のバージョン番号とマイグレーション

保存データ全体に `schemaVersion`(保存形式のバージョン番号)を付けます。
形式を変えたら番号を1つ上げ、「古い形式 → 新しい形式」に変換する関数を1つ書きます。
この変換を**マイグレーション**と呼びます。

```ts
// src/storage/migrations.ts (スケッチ)
export const CURRENT_SCHEMA_VERSION = 1;

// 「バージョン N のデータを N+1 に変換する関数」を、N を見出しにして並べる
const migrations: Record<number, (old: any) => any> = {
  // 1: (v1) => ({ ...v1, schemaVersion: 2, /* v1→v2 の変換 */ }),
  // 2: (v2) => ({ ...v2, schemaVersion: 3, /* v2→v3 の変換 */ }),
};

export function migrate(data: any) {
  let current = data;
  while (current.schemaVersion < CURRENT_SCHEMA_VERSION) {
    current = migrations[current.schemaVersion](current);   // 1段ずつ上げる
  }
  return current;
}
```

```
読み込んだデータ (schemaVersion: 1)
  | migrations[1]   v1 → v2
  v
(schemaVersion: 2)
  | migrations[2]   v2 → v3
  v
(schemaVersion: 3) = 現在の形式 → 中身の検査 → 画面や IndexedDB へ
```

1段ずつ上げる方式なので、どれだけ古いデータでも順番に通せば最新になります。

**マイグレーションを通す場面**

1. アプリの起動時(IndexedDB の中が古い形式だったとき)
2. JSON ファイルを読み込むとき(古いアプリで書き出したファイルも読める)

**使い分けの決まり**

| 変更の種類 | 例 | 対応 |
|---|---|---|
| 省略できる項目を足す | `gimmicks.tera` を足す | **番号は上げない**。読み込み時に初期値を補う |
| 名前や構造や意味を変える | `gimmicks` の形を作り直す | 番号を上げて、変換関数を書く |

- 読み込んだファイルの番号がアプリより**新しい**場合は読み込まず、「アプリを更新してください」と知らせる
- マイグレーションは純粋関数なので、「古い形式の例 → 期待する新しい形式」をテストで確かめられる
- IndexedDB 自体にも別の「バージョン番号」があるが、そちらは保存場所(ストア)を増やすときだけ上げる

### 6.7 具体例: もしテラスタルを追加するなら

| # | ファイル | 新規/変更 | 書くこと |
|---|---|---|---|
| 1 | `src/gimmicks/tera.ts` | 新規 | テラスタルの中身(下のコード) |
| 2 | `src/gimmicks/registry.ts` | 1行追加 | 登録簿に `tera` を並べる |
| 3 | `src/domain/individual.ts` | 1行追加 | `GimmickSettings` に `tera?: { teraType: string }` |
| 4 | `src/data/regulations.json` | データ変更 | 使えるレギュレーションの `gimmicks` に `"tera"` を足す |
| 5 | `src/features/gimmick-ui/TeraEditor.tsx` | 新規 | テラスタイプを選ぶ入力欄。UI の登録簿に1行追加 |
| 6 | `src/gimmicks/tera.test.ts` | 新規 | テスト |

**変更しなくてよいもの**: 能力値計算、ダメージ計算の流れの本体、保存とマイグレーション
(省略できる項目を足すだけなので番号も上げない)、個体一覧、チーム画面。

```ts
// src/gimmicks/tera.ts (将来のイメージ。今は作りません)
export const tera: Gimmick<{ teraType: string }> = {
  id: 'tera',
  label: 'テラスタル',
  canUse: () => true,   // どのポケモンでも使える

  // タイプを変える: 受けるときのタイプはテラスタイプ1つになる。
  // タイプ一致の判定に使う元のタイプ(stabTypes)はそのまま残す
  changeForm: (form, config) => ({ ...form, types: [config.teraType] }),

  // ダメージ補正を加える: テラスタイプと同じタイプの技にタイプ一致の上乗せ
  getModifiers: (config, ctx) =>
    ctx.side === 'attacker' && ctx.move.type === config.teraType
      ? [{ stage: 'stab', value: 2048, label: 'テラスタル' }]
      : [],

  // 技を変える: テラバーストのタイプ変更など
  changeMove: (move, config) =>
    move.id === 'tera-blast' ? { ...move, type: config.teraType } : move,
};
```

タイプ一致の段階は「4096 に上乗せを足していく」決まりにしておきます。すると、

- 元のタイプと一致: 4096 + 2048 = 6144 (1.5倍)
- テラスタイプだけ一致: 4096 + 2048 = 6144 (1.5倍)
- 元のタイプとテラスタイプの両方に一致: 4096 + 2048 + 2048 = 8192 (2.0倍)

となり、流れの本体を変えずにテラスタルの仕様を表せます。
`BattleForm` に `types` と `stabTypes` を分けて持たせたのは、このためです。

**ダイマックスなら**: `changeStats` で HP を2倍に、`changeMove` で技をダイマックス技に置き換えます。
ダイマックス技の威力は技ごとに決まっているので、`moves.json` に項目を1つ足します(データの追加)。

### 6.8 この設計の限界(正直なところ)

「既存コードの修正がゼロ」は約束できません。目標は**修正を最小限に、かつ1か所に集めること**です。

- 4種類のフックで表せない新しい変化が来たら、フックを1つ足す必要がある。
  ただし足す場所は `types.ts` と、フックを呼ぶ1か所だけ
- 特性とギミックが絡む特殊な決まり(例: テラスタル中の「てきおうりょく」)は、
  その特性のルール側にも数行の追記が要る
- テラスタルの細かい仕様(威力60未満の技の底上げ、特殊なテラスタイプなど)は、
  実装するときに改めて調べて確かめる。上のコードは仕組みを説明するための例

## 7. 計算の仕様

### 7.1 能力値

```
HP      = 種族値 + 75 + 能力ポイント
HP以外  = floor((種族値 + 20 + 能力ポイント) × 性格補正)
```

- 性格補正は小数で掛けず、**整数で計算**する(`× 11 ÷ 10` または `× 9 ÷ 10` してから切り捨て)。
  コンピュータの小数計算には小さな誤差があり、切り捨ての結果が1ずれるのを防ぐため
- 入力の制限: 各能力 0〜32、合計66まで。超える値は入力できないようにし、残りポイントを表示する

### 7.2 ダメージ

第9世代(スカーレット・バイオレット)本編の計算式を使います。
実装の手本は `@smogon/calc`(Pokémon Showdown のダメージ計算機、MIT ライセンス)で、
どの式を採用したかはコードのコメントに書きます。

用語: **五捨五超入** = 小数部分が 0.5 より大きいときだけ切り上げ(0.5 ちょうどは切り捨て)。

| # | 段階 | 内容 | 丸め方 |
|---|---|---|---|
| 1 | 威力 | 威力への補正を連鎖して掛ける(タイプ強化の持ち物、フィールドなど) | 五捨五超入、最低1 |
| 2 | 攻撃 | ランク補正 → 補正を連鎖(こだわりハチマキなど) | ランクは切り捨て、補正は五捨五超入 |
| 3 | 防御 | ランク補正 → 補正を連鎖(とつげきチョッキなど) | 同上 |
| 4 | 基礎ダメージ | `floor(floor(22 × 威力 × 攻撃 ÷ 防御) ÷ 50) + 2` | 切り捨て |
| 5 | 範囲 | ダブルで複数に当たる技 ×0.75 (3072) | 五捨五超入 |
| 6 | 天気 | ×1.5 (6144) または ×0.5 (2048) | 五捨五超入 |
| 7 | 急所 | ×1.5 | 切り捨て |
| 8 | 乱数 | ×(85〜100) ÷ 100 の16通り | 切り捨て |
| 9 | タイプ一致 | ×1.5 (6144) など | 五捨五超入 |
| 10 | タイプ相性 | ×0、×0.25、×0.5、×1、×2、×4 | 切り捨て |
| 11 | やけど | 物理技 ×0.5 | 切り捨て |
| 12 | 最終補正 | 壁、いのちのたま、半減のきのみ などを連鎖 | 五捨五超入 |
| 13 | 最低保証 | 無効でなければ最低1ダメージ | - |

- `22` は `floor(2 × レベル ÷ 5 + 2)` のレベル50での値
- 補正の「連鎖」: 2つの補正 a, b をまとめるときは `(a × b + 2048) ÷ 4096` の切り捨て
- 急所のときは、攻撃側の下がったランクと防御側の上がったランク、壁を無視する
- 壁はシングルで ×0.5 (2048)、ダブルで ×約0.667 (2732)。このためシングル/ダブルの切り替えを持つ

**チャンピオンズ固有の違いについて**: `@smogon/calc` の最新版(0.12.0)には、
チャンピオンズ専用の計算と、技などの変更データが含まれています。
ダメージ計算のステップで本編の式と見比べ、違いがあれば**勝手に変えずに報告して相談**します。

### 7.3 確定数

1発のダメージは16通りあります。n 発の合計がHP以上になる確率を、16通りの組み合わせから計算します。

- 最小ダメージ × n がHP以上 → 「確定 n 発」
- それ以外で倒せる可能性がある → 「乱数 n 発(xx.x%)」

## 9. データの入手方法とライセンス

### 9.1 入手先

| 入手先 | 取れるもの | ライセンス | 注意 |
|---|---|---|---|
| [PokéAPI](https://github.com/PokeAPI/pokeapi) の CSV | 種族値、タイプ、技、特性、持ち物、**日本語名** | BSD 3条項(プログラム部分) | 本編のデータ。チャンピオンズでの変更は入っていない |
| [@smogon/calc](https://github.com/smogon/damage-calc) | 計算式の手本。0.12.0 にはチャンピオンズの対象一覧と変更点 | MIT | 名前は英語のみ |
| ゲーム内の表示 | すべて | - | 最も確実。チャンピオンズ固有の値の最終確認に使う |

**進め方**: 数値は上の公開データから**補助プログラムで取得**し、手で写しません(写し間違いを防ぐ)。
取得元と取得日を `sources.json` に記録します。出典で確認できなかった値は**空欄のまま**にし、
推測で埋めません。チャンピオンズで本編から変わった技や特性があるため、
追加したデータは最後にゲーム内の表示と見比べてください。

### 9.2 ライセンス面の注意

これは一般的な情報であり、法律上の助言ではありません。

- ポケモンの名前・画像・ロゴは任天堂、クリーチャーズ、ゲームフリークなどの知的財産。
  上の表のライセンスは「そのプログラムやデータ集」に対するもので、ポケモンそのものの権利を与えるものではない
- **公式の画像・アイコン・ロゴは入れない**(このアプリは文字だけで作る)
- 公式と誤解される名前や見た目にしない。画面に「非公式のファンツール」と明記する
- 広告や課金を付けない(個人の学習用にとどめる)
- 使ったデータの出典とライセンス表記をリポジトリに残す(MIT や BSD は著作権表示の保持が条件)
- 攻略サイトの文章や表を、機械で大量に取得して使わない(各サイトの利用規約に反することが多い)

### 9.3 あとからデータを足す方法(予定)

1. 追加したいポケモンや技の ID を、対象一覧のファイルに書き足す
2. 補助プログラムを実行する → JSON に追記される
3. 検査プログラムを実行する → 項目の抜けや、存在しない ID の参照を見つける
4. ゲーム内の表示と見比べる

手で JSON に直接書き足すこともできます。その場合も 3 の検査で間違いを見つけられます。
